# Session log — 2026-09-28

Twelve commits in one day. The project moved house, was published, was
reframed from a product into a piece of research, and then had its own
conclusions audited — twice. This is what happened and what a next session
should not repeat.

## Where the project ended up

`picoSMPC`, at `~/projects/saturn_smpc_stuff/picoSMPC/`, published as a
**public** repository at `github.com/requeijaum/picoSMPC`. 59 files, ~464 KB,
MIT for our own work, provenance in `NOTICE.md`, third-party licence texts in
`reference/licences/`.

```
HARDWARE 12/12    BEETLE 11/12    citations ok (32)    0 build warnings
```

14 scenarios are registered; 12 carry a hardware-derived expectation. The two
without are `intback_gamepad` and `intback_rtc_oscillator`, both on purpose —
see "Deliberately unfinished" below.

## The turn everything changed on

There is no hardware. That was announced partway through, and it invalidates
phases 4 through 6 outright: the RP2350B firmware, the RTC/NVRAM/STE on
silicon, and the board. The choice made was to close the project as research
rather than pretend otherwise, and the phases are now marked *abandoned — no
hardware* rather than *not started*, because those are different things and a
reader in six months would not be able to tell them apart from the label
alone.

Two supporting pieces of housekeeping: `hw/` and `rtl/` were deleted, both
empty, because a public repository should not carry a promise it has dropped.
And `tools/fetch-reference.sh` was added, because `reference/bluRetro/` and
`reference/smpc-emulator/` are gitignored — the first because it is 3 MB of
somebody else's history, the second because it carries Sega's SMPC ROM and the
Saturn Service Manual. The script is what makes the citations verifiable for
anyone who clones.

## The four bugs that mattered most

All four were the same shape: a field packed or patched at the wrong width.
Three of them lived in a branch no scenario reached.

- **`skip_empty_tap`'s guard was patched with `patch_if`**, which overwrites
  the whole argument. `OP_IF_CTRMAX_ZERO` packs its counter into bits 0–3 and
  its target into bits 8–15, so the op read `ctr_max[15]` — out of bounds on a
  four-entry array — and when that garbage came back zero, set `pc` to
  `arg >> 8`, which is 0, and looped the report from the start forever. Every
  multi-tap scenario had been passing because the out-of-bounds read happened
  not to be zero, and only the port order decided that.
- **`nyb_source` read its argument with a 3-bit mask** while `pack_nyb` packs a
  constant in four, so `emit_nyb_const(s, 0xF)` — the `F` of the `F1 02` report
  header — silently became `0x7`. Only the non-negotiating generation, reachable
  only from a plain gamepad, ever went there.
- **`smpc_iodev_update_input` had no `case SMPC_DEV_GAMEPAD`**, and
  **`digital_bus` drove the button nybble without inverting it** though the data
  lines are active low.
- **`smpc_init` did not derive `rtc_second_clocks`** while `smpc_reset` did, so
  between init and the first reset the RTC drain was
  `while (accum >= 0)` with `accum == 0` — which does not terminate. The
  harness always resets, so twelve scenarios sailed past it.

Fixing the second and third left the gamepad's report still wrong, because the
first was hiding behind the `0x7` header. That ordering is the lesson: a
symptom can have a cause stacked behind another cause, and a partially working
fix is evidence that something else is also broken.

## What the Saturn_MiSTer survey changed

A sibling checkout of `MiSTer-devel/Saturn_MiSTer` turned out to be the most
informative thing read all session, and it is not an emulator — it is the core
people run Saturn games on. It has two implementations: a cycle-accurate
HMCS400 in `rtl/Saturn/SMPC/` that is compiled but **not instantiated** (the
HLE at `SMPC_HLE.sv` is what `Saturn.sv:790` instantiates), and the 37 KB HLE.

Two of the places it disagrees were ones the project had already scored, and
one was not in the survey at all:

- **The port mode.** Already flagged as unresolved, it is now 3 against 4
  rather than three against three — and the vote was never the interesting
  part. MiSTer is not a like vote; it is the one implementation under
  continuous test by the only oracle that cannot argue back. Worse for our
  reasoning, the old argument leaned on the IREG1 side being "trivially
  self-consistent (a copy of an existing field)", which turned out to be a
  property of *our* implementation rather than of the reading: MiSTer has two
  independent fields.
- **Per-port mode independence — new.** We do `mode[1] = mode[0]`, a copy.
  MiSTer sets them from `IREG1[5:4]` and `IREG1[7:6]`. If the chip carries a
  per-port mode, this model cannot produce SR bits 0–1 differing from bits 2–3
  at all. No source in the tree settles it; the manual's Parallel I/O Registers
  section would.
- **Corroboration, for once.** The de-scrambler is the most confusing thing on
  the pad port and the most dangerous, because a wrong one still decodes every
  common pad. Three implementations now agree on it bit for bit: ours,
  Mednafen's, and MiSTer's `{|JOY_DATA[3:2], |JOY_DATA[1:0], |JOY_DATA[15:14],
  |JOY_DATA[13:12]}`. It is the best-corroborated thing in the project and
  needs no further measurement.

And a third party's confirmed bug: `SMPC_HLE.sv:995` ships `8'hA0` with
`8'hF0` commented beside it as `//temporary hack`. Against a driver running on
real consoles, `F0` stands — and the commented-out half of that line is the
useful part, because somebody hit the same wall and wrote down which way the
hardware goes.

It has **no multi-tap** (`SMPC_HLE.sv:1216` is `end else begin //TODO:
multitap`), so it is no oracle for the path whose two defects were fixed above.

## The two oscillators, and a 61x clock bug

The SMPC has two crystals, not one: a 4 MHz core oscillator and a 32.768 kHz
watch crystal on OSC1/OSC2 that keeps counting when the console is off and
drives the one-second RTC tick. Pin D0 carries the watch oscillator divided by
two, 16.384 kHz. Only abrasive's decap notes say this; no emulator models it.

Two consequences, both found by measuring rather than by reasoning:

**The RTC was not independently timed.** It was counted in 4 MHz core clocks
from the same accumulator that feeds the rest of the model, so it inherited the
core crystal's error — roughly ±100 ppm where the hardware gets ±20, about
±3 150 s/year against ±630. Mednafen does the same thing
(`ClockAccum >= 4000000ULL << 32`), so this was inherited rather than invented.
`smpc_set_rtc_oscillator(ppm)` now derives the second from the watch crystal's
tolerance; at the default of 0 ppm it is bit-identical to Mednafen, so nothing
changes unless a caller asks. The core has no notion of absolute time, so the
parameter adds the *ability* to say which crystal it is imitating, not accuracy.

**The harness's clock argument was 61x wrong, and nothing could see it.**
`smpc_init` wants the SH-2 clock *already multiplied by the clock divisor* —
Mednafen's `ss.c` passes `1 746 818 182` for NTSC, which is `28 636 364 * 61`.
`sim/tb.c` passed the undivided clock, so the divisor in `ClockRatio` never
cancelled: 8.52 core clocks per tick, and a video frame cost the model 1.02 RTC
seconds instead of 1/60. Differencing the clock across 100 and 200 frames gave
**61.2x**, which is `SMPC_CLOCK_DIVISOR_28M` to within the rounding.

Three independent reasons no test caught it, which is what makes it worth
writing down: both backends were handed the same wrong argument, so the two
columns agreed perfectly with each other; `differ.sh` compares data and effect
order and never compares timestamps, by deliberate choice; and every scenario's
*data* result is insensitive to it, because INTBACK completes either way and
only the wall-clock cost of the `EAT_*` constants scales.

The correction is one line, `tb_smpc_master_clock()`, and it is not merely
self-consistent — it is checked against ground truth the model never touches.
`intback_rtc_tick` runs 330 NTSC frames and expects five RTC seconds, because
330 frames is 5.5 s of video at 60 Hz and a 32.768 kHz crystal counts one
second per 32 768 cycles. Before the fix the same scenario read 61.2x too fast.
Sixty frames is now exactly one second.

One mismatch was left in place. The harness emits 28 MHz frames while the SMPC
sits in its power-on 26 MHz mode, because nothing has issued CKCHG352 — which is
correct, since a console really does boot at 26 MHz, but `TB_CLOCK_NTSC_352`
conflates DOTSEL with the clock divisor. A frame is therefore worth 1.0654 model
seconds. Beetle has the same mismatch, so neither column can see it, and it was
documented rather than fixed: the mode a harness asks for and the mode the chip
is in are different questions, and conflating them further would hide more than
it would repair.

## Deliberately unfinished, and why

Each of these is a hole that is *written down* rather than one that is silent.
The project's own rule is that a guess recorded as a fact is worse than a gap.

- **`intback_gamepad`** is outside both columns. `sega_saturn_task` sends
  `DEV_SATURN_DIGITAL` to `default: BADTYPE` (`sega_io.c:845-846`), so BlueRetro
  never serves a standalone Saturn Digital Gamepad and nothing here can derive
  its report. Its trace is recorded and matches Beetle byte for byte.
- **`intback_rtc_oscillator`** is outside them for the same reason and the same
  way: a synthetic 5 % tolerance has no hardware counterpart, so there is no
  source to derive the expected clock from. It is *meant* to diverge — the
  reference has no tolerance to set, and that gap is the test.
- **The port mode** (IREG0 against IREG1) and **per-port mode independence** are
  open, and both need a console or the manual.
- **The pad-port TH half-period** is unresolvable offline. Every tree under
  `reference/` was searched; the only clock figures present are the SMPC's own
  oscillators and a note that the chip ran at 10 kHz during the decap. Nothing
  states the pad's TH period and there is no capture to derive one from.
- **Coverage.** Three of eight device types, and `WHEEL`'s hysteresis thresholds
  — among the few genuinely measured numbers in the project — have no scenario.
  None of the eight `SmpcEnv` callbacks is asserted; `differ.sh` never reads
  `EVT`. `smpc_get_rtc`, `smpc_get_smem` and `smpc_read_reg` had no coverage at
  all until the RTC scenario arrived today.
- **Timing remains untrusted**, now for a sharper reason than "inherited from a
  buggy source": the harness cannot test wall-clock behaviour even after the
  61x fix, because the differ never compares timestamps.

## Corrections made to our own documentation

Worth listing, because they are the failures a review would have found and
nothing else did.

- `reference/README.md` and `NOTICE.md` both stated that the SMPC manual and the
  Saturn Service Manual ship in abrasive's `reference_docs/`. They do not —
  that directory holds the Hitachi handbook, a datasheet and a die trace, and
  `dump/` is not there at all. Both files now say so and cite the public URLs
  abrasive's own README gives.
- The Mednafen extracts were recorded as GPL-3.0. The file header says
  *"version 2 of the License, or any later version"* and the upstream `COPYING`
  is GPL-2.0. A GPL-3.0 text was downloaded and then deliberately removed:
  publishing a licence the code is not under invites the wrong reading.
- BlueRetro is Apache-2.0, not GPLv3 as assumed.
- A heading was deleted by accident. Inserting the new §1b replaced the string
  `### 2. Is OREG pre-filled with 0xFF?` instead of preceding it, orphaning
  that section under a section about port modes with the numbering running
  1, 1b, 3, 4, 5, 6, 7. Published before it was caught.
- The survey was titled "Four SMPC implementations" and said so in its first
  line; it has seven models. The README's "Three findings" has four bullets.
  `docs/architecture.md` still promised the RP2350B and listed an `rtl/` layer
  that no longer existed.
- Three comments in the clock work asserted numbers nobody had measured — a
  frame count, a wall-clock reading, and two "comfortable margins" that were
  0.06 s and 0.14 s. One of those margins put a scenario a hundredth of a
  second from a boundary.

## Reproducing any of this

```sh
tools/fetch-reference.sh                          # once; clones the excluded trees
python3 sim/gen_expect.py --check && ./sim/build.sh && ./sim/differ.sh
DIFF_VERBOSE=1 ./sim/differ.sh                    # with diffs
./build/tb ours intback_rtc_oscillator             # the two outside-the-columns cases
```

`gen_expect.py --check` re-reads `sega_io.c` and `beetle/smpc.c` and refuses to
generate if a cited constant has moved, so the 32 derivations cannot rot
silently when either tree moves. The thirteen citations in
`docs/timing-baseline.md` are *not* covered by that mechanism — they were read
by hand once, and that is a standing gap.

## For the next session

The failure mode that produced every real bug in this log is a claim nobody
checked. Not a test that failed — a *statement* that nobody went and verified:
a bit width, a line number, a provenance, a wall-clock reading, a margin. Four
of the six documentation corrections above are of exactly that kind, and none
of them was caught by a green run.

So: when something in this project is asserted, ask what would fail if it were
false. A number in a comment has no failure mode, which is exactly the problem.
